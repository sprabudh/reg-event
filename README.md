# Eventora 🎟️

A full-stack event management, ticketing and event-approval platform. Eventora lets **attendees** browse a catalog, book seats (with automatic waitlisting), receive QR-coded digital tickets, and cancel under a refund policy; **hosts** submit events for review and then manage their own event's attendees, payments and door check-ins; **admins** create events directly, curate categories, review the host approval queue, and oversee payments and refunds.

Built with Spring Boot and React.

**Frontend:**

- Java 21 / Spring Boot 4.1 (`pom.xml`)

- jjwt 0.11.5 — access + refresh token signing
- Google ZXing 3.5.3 — QR code rasterisation to PNG
- Jakarta Bean Validation — entity and DTO constraints

- springdoc-openapi (dependency present; see [Notes & Known Limitations](#-notes--known-limitations))

**Database:**
- PostgreSQL 16 (containerised via Docker Compose)
- Schema generated by Hibernate — `ddl-auto=update`, no migration files

## 👥 Roles

Three roles, defined in `user/Role.java`:

| Role | Sign-up path | Purpose |
|------|--------------|---------|
| `USER` (attendee) | `/register` → **Attendee** | Browses the catalog, books seats, holds tickets |
| `HOST` (event manager) | `/register` → **Host** (must use an `@eventora.com` email) | Submits events for approval, then manages attendees / payments / check-in for their **own** events only |
| `ADMIN` | Seeded, or `/admin-setup` by an existing admin | Creates events directly, curates categories, runs the approval queue, sees all payments |

### Host approval workflow

Hosts cannot publish directly. Every host submission is persisted immediately but held at `PENDING`, and is filtered out of every attendee-facing query until an admin approves it:

```
Host submits ──► approval_status = 'PENDING'  (visible to the host + admin queue only)
Admin approves ──► approval_status = 'APPROVED'  (now matches the attendee catalog query)
Admin rejects ──► approval_status = 'REJECTED'  (host sees the rejection reason)
```

**Approval *is* the publish step** — there is no separate "go live" flag. Categories deliberately have **no** approval queue: they stay admin-owned, and a host picks from the same list when submitting.

## ✨ Features

### Authentication & Security

- **JWT authentication** with `Authorization: Bearer <token>` on every protected endpoint.
- **Access + refresh token pair.** Access tokens live 15 minutes; refresh tokens 7 days. The access token is the only one accepted for API calls — a refresh token carries a `typ: REFRESH` claim and is rejected by `JwtAuthenticationFilter`.
- **Refresh-token rotation.** Every refresh and every logout *revokes* the presented token server-side, so a stolen copy is usable at most once.
- **Silent token refresh in the client.** A 401 triggers one shared refresh + request replay; the user never sees an expiry. Parallel 401s share a single in-flight refresh so rotation cannot log them out mid-session. The session only ends when the refresh itself fails.
- **Revocation is real.** Only a SHA-256 hash of each refresh token is stored (`refresh_tokens.token_hash`, unique-indexed), so a database dump cannot be replayed as a live session.
- **Sign out / sign out everywhere.** Logout revokes the presented token; omitting it revokes every live session for the caller. Both always answer `204`.
- **Password hashing** via BCrypt — plaintext is never stored or logged, and `@JsonIgnore` keeps the hash off the wire.
- **Host email-domain gate.** Host signups require `@eventora.com`, configurable via `application.security.auth.host-email-domain`. Blank disables the rule.
- **Login account-type selector.** Picking "Host" for an attendee account (or vice versa) is rejected server-side; `ADMIN` is exempt so admins can use either door.
- **Admin creation is admin-only.** `POST /api/auth/register-admin` requires `ADMIN` — only an existing admin can mint another.
- **Password policy** enforced identically on both stacks: ≥8 characters, one uppercase, one lowercase, one digit, one symbol.

### Events

- **Three creation paths, one form.** `EventForm.jsx` serves admin-create, admin-edit, host-submit and host-edit, branching on role and route params rather than duplicating pages.
- **Auto event expiry.** An event is *ended* once its date + start time (`HH:mm`) + duration (`"2h"`, `"90 min"`, `"2h30m"`) have passed. Ended events are hidden from attendee views, blocked from new registrations (`400`), flagged with an **"Ended"** badge, and rejected for create/edit (`400`) — no manual admin action.
- **Delete guard.** An event cannot be deleted while any attendee is registered (`409`).
- **Category linkage.** Every event requires a category; category deletion is blocked while events reference it (`409`). An idempotent `"Other"` fallback category is seeded at startup so nothing is ever un-categorisable.
- **Server-set ownership fields.** `hostedByUserId`, `hostName`, `approvalStatus`, `approvedByUserId`, `approvedAt`, `rejectionReason` and `id` are always overwritten server-side on create, so a hand-crafted request cannot self-approve an event or claim ownership of someone else's.
- **Ownership enforcement.** Every `/api/host/**` read and write resolves the caller from their JWT and rejects events they do not host (`403`).
- **Search + category filter + pagination** on both the admin and attendee catalogs, with sorting by nearest event date and a stable `id` tiebreaker.
- **Availability stats** per event: `{ capacity, registered, available }`.

### Registration, Capacity & Waitlisting

- **Capacity-aware booking.** Only `CONFIRMED` and `CHECKED_IN` seats count toward capacity.
- **Automatic waitlisting.** When the event is full the registration is created as `WAITLISTED` — no ticket, no charge.
- **FIFO auto-promotion.** Cancelling a confirmed seat promotes the single oldest waitlisted registration (by `registration_date`), issues it a ticket, and auto-creates the paid invoice for paid events. No manual "admit from waitlist" action exists.
- **Duplicate-registration guard** per `(email, event_id)` — both in the service (`409`) and as a DB unique constraint, with a `DataIntegrityViolationException` → `409` fallback for races.
- **Closed-event guard.** Registration on a `PENDING`/`REJECTED` event is refused (`403`), as is registration on an ended event (`400`).
- **Input validation.** Mobile numbers must be exactly 10 digits; event dates must be today or later; capacity must be positive; event name cannot be blank.

### QR Ticketing

- **Automatic QR ticket generation.** On confirmation, a cryptographically random type-4 UUID is minted and encoded as a 200×200 PNG QR via ZXing, returned as a ready-to-render `data:image/png;base64,…` URI.
- **The QR payload is the ticket UUID** and nothing else. It is stored on a unique column and never regenerated by an edit — a cancel/re-register always produces a fresh ticket.
- **Ticket display** on the event detail page and the My Tickets page, including a graceful "Ticket Unavailable" placeholder for legacy rows with no ticket ID.
- **Print / Save as PDF** — a dedicated print view opens in a new window with every interpolated value HTML-escaped and the browser print dialog triggered on load.

### Day-Of Check-In

- **Ticket scan by UUID** — the ticket must belong to that specific event.
- **Date guard.** Check-in is only permitted on the **exact calendar date** of the event (server local time); the event's start time and duration are not considered.
- **Duplicate prevention.** An already-`CHECKED_IN` attendee is refused.
- **Status guard.** Only `CONFIRMED` registrations can be checked in — a waitlisted attendee is refused.
- **Legacy guard.** Registrations predating ticketing have no UUID and are surfaced with an explicit message rather than a silent failure.
- **Double-click protection** on both the admin and host check-in buttons.

### Payments, Refunds & Cancellations

- **Auto-invoicing.** Every paid registration creates a `payments` row with a unique invoice number `INV-{year}-{6-digit-id}`, amount, `PAID` status and timestamp. Free events create no payment row.
- **Per-event payment history** (admin, and the owning host): invoice, attendee, amount, payment date, refund status, cancellation date — newest first.
- **Refund policy per event.** Cancelling a paid registration sets the payment to `REFUNDED` on refundable events and `FORFEITED` on non-refundable ones, and stamps `cancelled_at`.
- **Free and legacy cancellations** get a ₹0 record with a **"No Refund (Free)"** badge.
- **Waitlisted cancellations create nothing** — no synthetic row, no payment update.
- **Cancellation is a hard delete of the registration**; the payment row is retained as financial history.
- **Cancellation prompts state the policy and amount** before the user confirms (e.g. *"Your ₹500 fee will be refunded within 3 working days"* vs *"This is a NON-REFUNDABLE event. Your ₹500 fee will NOT be refunded."*).
- **Authorization on cancellation.** Admins may cancel anything; hosts only registrations on events they host; attendees only their own.

### Attendee Self-Service

- **My Tickets** — confirmed and checked-in registrations only (waitlisted ones are deliberately hidden), each with QR code, event details, status badge, payment amount, invoice number and refund badge, paginated and sorted by event date.
- **Edit own registration** — name and mobile number are editable; **email is immutable** for regular users (`403`), and no edit is permitted after check-in.
- **Duplicate-email re-check** when an admin or host changes an email on a registration (`409`).

### Dashboards & Navigation

- **Role-aware dashboard hero and metrics.** Admins see *Ended Events* and *Approval Pending*; hosts see *My Hosted Events* and *Pending Requests*; attendees see only *Total Active Events*.
- **Latest Opportunities** — newest active, non-expired events the viewer has not already registered for.
- **Failure isolation.** Dashboard metric fetches use `Promise.allSettled`, so one failing role-specific call cannot blank out the other metrics.
- **Role-aware header** with the current role badge, role-appropriate nav links, and a confirm-guarded logout.

### Frontend Engineering

- **One axios instance** (`services/api.js`) — base URL, bearer injection and token refresh live in one file, so no component or service ever touches storage.
- **Layered architecture** — page (smart) → hook (state/orchestration) → service (one function per API intent) → api client. Reusable `ui/` primitives are stateless.
- **Shared auth form hook** (`useAuthForm`) with Zod resolvers, so Login and Register cannot drift apart.
- **Promise-based confirm dialog provider** — `await confirm({...})` suspends on a real modal (focus trap, Escape, scroll lock, focus restore) instead of `window.confirm`. Superseded prompts auto-decline so no caller hangs.
- **Toast helper** (`useFlash`) with unmount-safe timer cleanup.
- **Accessibility:** skip link, `<main>` landmark, `aria-modal` dialog, `role="alert"` / `role="status"` banners, `aria-label` / `aria-invalid` / `aria-describedby` on inputs, label-to-control id pairing via `useId`, screen-reader table headers.
- **Race-condition guards:** request-sequence ids on the events list, out-of-order response protection, render-time page clamping so the last page never renders empty.
- **Centralised constants** — routes, endpoints, roles, pagination sizes, messages and badge classes all live in `constants/`, kept in step with their backend twins.

## 🗄️ Database Schema

Tables are created and evolved by Hibernate on startup (`spring.jpa.hibernate.ddl-auto=update`). **There are no SQL migration files** — see [Notes & Known Limitations](#-notes--known-limitations).

| Table | Purpose |
|-------|---------|
| `users` | Accounts: name, unique email, BCrypt password, role (`USER` / `ADMIN` / `HOST`) |
| `categories` | Admin-owned event categories, unique name (includes the seeded `"Other"`) |
| `events` | Name, `event_date`, `time`, `duration`, `capacity`, `category_id` FK, location, price, `is_online`, `is_refundable`, plus the host + approval columns: `hosted_by_user_id`, `host_name`, `approval_status`, `approved_by_user_id`, `approved_at`, `rejection_reason` |
| `attendees` | Registrations: name, email, `mobile_number`, `registration_date` (`@CreationTimestamp`), `event_id` FK (lazy), `status`, unique `ticket_uuid`, `qr_code` (TEXT data-URI). Unique on `(email, event_id)` |
| `payments` | Invoice history: unique `invoice_no`, `attendee_id`, `event_id`, amount, `status`, `paid_at`, `refund_status`, `cancelled_at`, plus denormalised attendee/event name snapshots |
| `refresh_tokens` | Issued sessions: unique indexed `token_hash` (SHA-256 hex), `user_email`, `issued_at`, `expires_at`, `revoked` |

### Enum values

| Enum | Values |
|------|--------|
| `Role` | `USER`, `ADMIN`, `HOST` |
| `ApprovalStatus` | `PENDING`, `APPROVED`, `REJECTED` |
| `RegistrationStatus` | `CONFIRMED`, `WAITLISTED`, `CHECKED_IN`, `NOT_IN` |
| `RefundStatus` | `NONE`, `REFUNDED`, `FORFEITED` |

> **Cancellation is not a status.** The `attendees` row is hard-deleted and the `payments` row is retained. There is no `CANCELLED` enum value.

## 🛠️ Local Setup & Installation

### Prerequisites
- Docker Desktop
- **Java 21+**
- Node.js & npm

### 1. Start the Database

```bash
docker compose up -d
```

The container (`event-postgres-db`, PostgreSQL 16-alpine) maps internal `5432` → host **`5434`**, with `eventuser` / `eventpass` and database `eventdb`. Data persists in the `pgdata` volume.

### 2. Start the Backend

```bash
./mvnw spring-boot:run
```

Runs on `http://localhost:8080`. On first start the seeder prints confirmation lines for the master admin and the fallback category.

### 3. Start the Frontend

```bash
cd frontend
npm install
npm run dev
```

Runs on `http://localhost:5173`.

### Useful commands

| Command | Purpose |
|---------|---------|
| `npm run dev` | Vite dev server (HMR) |
| `npm run build` | Production bundle into `frontend/dist` |
| `npm run lint` | ESLint |
| `./mvnw spring-boot:run` | Start the API |
| `./mvnw test` | Run backend tests |
| `docker compose down` | Stop the database |

### Error envelope

| Code | Meaning |
|------|---------|
| `400` | Validation failure, ended event, malformed request |
| `401` | Missing/expired token, bad credentials, wrong account type, dead refresh token |
| `403` | Authenticated but not permitted (ownership, closed event, email change, post-check-in edit) |
| `404` | Event or attendee not found |
| `409` | Duplicate registration, event full, delete-while-in-use, category in use, already checked in |
| `500` | Unexpected fault (generic message; details are logged, never returned) |

Validation failures return a per-field map so the UI can render inline errors:

```json
{
  "timestamp": "...",
  "status": 400,
  "message": "Validation failed",
  "errors": { "name": "Name is required", "capacity": "Capacity must be greater than 0" }
}
```

Responses travel back the same way and are projected into DTOs before serialization.

## ⚠️ Notes & Known Limitations

Documented so the behaviour is not surprising:

- **No schema migrations.** `ddl-auto=update` adds columns but never backfills them. Every event created before the approval feature has `approval_status = NULL`, which is why `searchApprovedEvents` filters `(approval_status IS NULL OR approval_status = 'APPROVED')` — otherwise the entire pre-existing catalog would silently disappear. Introduce Flyway before this reaches production.
- **The JPA entity is the request/response body for events.** `EventController` / `HostEventController` bind `Event` directly, so clients *can* send privileged fields; the services overwrite them all, but the safety depends on that remaining true for every new column. `dto/EventRequest.java` exists but is unused — migrating to request/response DTOs would close this properly.
- **`EventService` has no `@Transactional`.** `deleteEvent`'s "no attendees" check is not atomic with the delete, so two concurrent registrations can race it.
- **No state-machine guard on approve/reject.** `approveEvent` does not verify the event is currently `PENDING`, so a `REJECTED` event can be re-approved.
- **`capacity` is not coerced on the client** (unlike `price`), so a blank value returns a generic `400` with no per-field message.
- **`isVisibleToAttendees()`** is dead code — the same rule is already in the repository query — yet Jackson still serializes it onto every event response as `visibleToAttendees`.
- **Check-in status codes differ by route.** The admin path collapses every failure into `400`; the host path surfaces the real `404`/`409`.
- **springdoc-openapi is a dependency but is not reachable** — `SecurityConfig` sends `/swagger-ui/**` and `/v3/api-docs/**` to `anyRequest().authenticated()`, and CORS does not allow them. Add `permitAll()` if you want the API docs.
- **`RegistrationStatus.NOT_IN`** is declared but never assigned anywhere.
- **`EventFullException`** exists but is never thrown — full events are waitlisted rather than rejected.
- **Search is per-page for the host catalog**, which loads up to 40 rows and paginates client-side; the admin and attendee catalogs page server-side.

## 🗺️ Roadmap

- **Schema migrations:** adopt Flyway/Liquibase and backfill the legacy `approval_status` rows, then drop the `IS NULL OR` fallback.
- **Request/response DTOs for events** to remove the entity-as-payload mass-assignment surface.
- **Transactional service methods** plus a real approval state machine (`PENDING → APPROVED | REJECTED` only).
- **Automated email ticketing** via `spring-boot-starter-mail`, delivering the QR ticket on registration and waitlist promotion.
- **Financial reporting:** per-platform revenue, refunds and active-bookings totals (currently only per-event payment history exists).
- **Admin data export** — CSV/Excel downloads of attendee and payment lists for offline door management.
- **Waitlist management:** manual promotion or bulk notification beyond the current automatic single-seat FIFO promotion.
- **Owner transfer** for events when a host account is deactivated.
- **Rate limiting and brute-force protection** on the auth endpoints.
- **Token revocation on password change**, and moving the refresh token to an `HttpOnly` cookie.
